# Recycling — LR3

Учебное REST API для учёта сдачи вторсырья на Java 17, Spring Boot 3.5.4, Spring Data JPA, Maven, Lombok и MySQL.

## Сущности и связи

- `User` — пользователь; один пользователь может иметь несколько партий (`RecyclingBatch`).
- `RecyclingType` — тип материала, единица измерения и баллы за килограмм.
- `CollectionPoint` — пункт приёма, принимаемые типы, доступность и дневной лимит.
- `RecyclingBatch` — партия, связанная с одним пользователем, одним пунктом и одним типом материала.
- `BonusEntry` — начисление баллов; для одной партии может существовать максимум одна запись.
- Между `CollectionPoint` и `RecyclingType` связь многие-ко-многим через `collection_point_types`.

JPA создаёт таблицы и внешние ключи. Сервисный слой дополнительно проверяет правила предметной области.

## Запуск

1. Установите JDK 17, Maven и MySQL. Стиль сущностей, сервисов и контроллеров ориентирован на учебный пример преподавателя: JPA-аннотации, Lombok (`@Getter`, `@Setter`, `@NoArgsConstructor`, `@AllArgsConstructor`, `@RequiredArgsConstructor`) и внедрение зависимостей через `final`-поля.
2. Откройте `db/create_app_user.sql` в MySQL Workbench под администратором. Замените `REPLACE_WITH_STRONG_PASSWORD` на свой локальный пароль и выполните скрипт. Пользователь `recycling_app` получает права только на базу `recycling`.
3. Откройте проект в IntelliJ IDEA как Maven-проект через `pom.xml`. Если Lombok-подсказки не отображаются в редакторе, проверьте поддержку Lombok в IntelliJ; Maven при сборке использует настроенный annotation processor.
4. В **Run → Edit Configurations… → Environment variables** задайте `DB_USERNAME=recycling_app;DB_PASSWORD=ВАШ_ПАРОЛЬ`.
5. Обновите Maven-зависимости и запустите `RecyclingApplication`.

`src/main/resources/application.yaml` читает пароль из переменной окружения, а не хранит его в исходном коде. Hibernate использует `ddl-auto: update`, чтобы обновлять схему учебной базы. `.env.example` — только образец: Spring Boot автоматически его не загружает.

## REST API

Базовые пути:

| Сущность | Путь |
|---|---|
| Пользователи | `/api/users` |
| Типы вторсырья | `/api/recycling-types` |
| Пункты приёма | `/api/collection-points` |
| Партии | `/api/recycling-batches` |
| Начисления | `/api/bonus-entries` |

У каждой сущности есть `GET` (список), `GET /{id}`, `POST`, `PATCH /{id}`, `DELETE /{id}`. Удаление может быть запрещено, если объект используется другими записями. Для создания пункта приёма указывайте `acceptedTypes` с существующими идентификаторами типов, например `[{"id": 1}]`.

## Пять бизнес-операций

1. **Зарегистрировать сдачу** — `POST /api/recycling-batches/business/register`. Тело: `{"userId":1,"pointId":1,"recyclingTypeId":1,"mass":5.0,"collectionDate":"2026-10-17"}`. Проверяются связанные записи, масса, доступность пункта, принимаемый материал и дневной лимит.
2. **Подтвердить приём** — `POST /api/recycling-batches/{id}/confirm`. Меняет статус партии и создаёт начисление `масса × pointsPerKg` в одной транзакции.
3. **Отклонить сдачу** — `POST /api/recycling-batches/{id}/reject`. Допустимо только для ожидающей партии.
4. **Перенести партию** — `PATCH /api/recycling-batches/{id}/transfer`, тело `{"pointId":2}`. Проверяет новый пункт, тип материала и его дневной лимит.
5. **Отменить принятую сдачу** — `POST /api/recycling-batches/{id}/cancel`. В одной транзакции меняет статус партии и аннулирует связанную запись баллов.

Статусы партии: `Ожидает`, `Принята`, `Отклонена`, `Отменена`. Создание всегда начинает с `Ожидает`; прямое изменение статуса через CRUD не допускается. Повторное подтверждение, повторное отклонение и повторная отмена отклоняются. Операции, меняющие партию и начисление одновременно, помечены `@Transactional`.

## Postman и проверка

Импортируйте `postman/Recycling_LR3.postman_collection.json`. Запустите папку **«Основной сценарий (запускать сверху вниз)»** по порядку: создание данных → регистрация → перенос → подтверждение → проверка начисления → отмена → отклонение второй партии. Папка **«Проверки ограничений»** должна возвращать HTTP 409 для повторных/недопустимых действий и превышения лимита. CRUD-примеры сгруппированы отдельно и запускаются выборочно. Для записей начислений после основного сценария предусмотрены проверки: повторное начисление за отменённую партию и изменение аннулированного начисления должны возвращать HTTP 409; удаление аннулированного начисления — HTTP 204. Запускайте эти три запроса в конце, поскольку удаление убирает запись начисления.

Дополнительные ограничения: масса и дневной лимит должны быть положительными; пункт обязан принимать указанный материал; активные партии `Ожидает` и `Принята` учитываются в дневном лимите; баллы рассчитывает сервер; нельзя удалить пользователя/пункт с партиями или тип материала, который ещё используется. Нельзя менять тариф баллов, пока есть принятые партии этого типа: это сохраняет соответствие уже начисленных баллов тарифу.


## Задание 4. Spring Security

В проект добавлены HTTP Basic, CSRF-защита, регистрация с хешированием пароля BCrypt и роли `USER` / `ADMIN`.

### Первый запуск после обновления

1. Запустите приложение и откройте коллекцию `postman/Recycling_LR3.postman_collection.json`.
2. В папке **«Аутентификация и CSRF»** сначала выполните запрос **«Получить CSRF-токен»**, затем **«Зарегистрировать пользователя»**. Регистрация создаёт пользователя с ролью `USER`.
3. Для лабораторной работы назначьте одному тестовому аккаунту роль администратора вручную через MySQL Workbench. Например, если зарегистрирован логин `admin`:

   ```sql
   UPDATE users SET role = 'ADMIN' WHERE username = 'admin';
   ```

   Назначение администратора не доступно через API регистрации. Не выполняйте запрос для обычного пользователя.
4. В переменных коллекции Postman укажите `authUsername` и `authPassword`. Для административных запросов используйте учётную запись с ролью `ADMIN`; для проверки обычного пользователя укажите логин и пароль аккаунта с ролью `USER`.
5. Скрипт коллекции получает CSRF-токен перед запросом и добавляет его в нужный заголовок. При ручном выполнении запросов сначала вызовите `GET /api/csrf-token`, сохраните cookie сессии и передавайте возвращённые `headerName` и `token` во всех POST, PATCH и DELETE запросах.

### Права доступа

- `USER`: может зарегистрироваться, просматривать только свои партии и создавать партии от своего имени через `/api/recycling-batches/business/register`.
- `ADMIN`: может управлять пользователями, типами вторсырья, пунктами приёма и начислениями; просматривать все партии и выполнять операции подтверждения, отклонения, переноса и отмены.
- Регистрация не позволяет задавать роль или парольный хеш в запросе. Пароль хранится в базе только в виде BCrypt-хеша.
- Ошибки отсутствующей аутентификации возвращаются с кодом `401`, а недостаточных прав или отсутствующего CSRF-токена — с кодом `403`.

### Важное замечание о существующей базе

Существующие записи таблицы `users` сохраняются. У ранее созданных записей поля `username`, `password_hash` и `role` останутся пустыми, поэтому они не смогут входить в систему до отдельной настройки. Для входа создайте новые учётные записи через регистрацию.
